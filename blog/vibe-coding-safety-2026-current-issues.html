The incidents that made this year different

Abstract vulnerability rates are easy to shrug off. These five aren't abstract — they're what happens when the statistics above land on a real app with real users.

1Moltbook — a public key with no lock behind it January 2026

An entrepreneur launched an "agent-first" social network — built entirely by prompting AI, by his own account without writing a line of code — where only AI agents could post and comment. Within days, researchers found the Supabase API key sitting in plain sight in the client-side JavaScript, with no Row-Level Security policy on the database behind it. Anyone could query the production tables directly. The result: roughly 1.5 million API authentication tokens exposed, along with 35,000 email addresses and thousands of private messages. Because those tokens worked like passwords for the platform's AI agents, exposing them meant anyone could impersonate any agent on the network.

The lesson: this is the exact Supabase-RLS failure this blog has described before — just running at agent-network scale. A public key was never the risk; the missing database rule behind it was.

2Lovable's own platform leaked its users' data Feb–Apr 2026

This one matters more than most, because the affected system wasn't a side project — it was Lovable, one of the platforms people use to vibe-code, valued at $6.6 billion. A researcher reported an authorization flaw through Lovable's own bug bounty program in February; the reports were closed without escalation, and the flaw stayed live for close to eleven weeks before Lovable publicly acknowledged and fixed it. During that window, anyone with a free account on the platform could read other users' source code, database credentials, AI chat history, and customer data. Because vibe-coded apps routinely embed third-party keys — Supabase, Stripe, Google — directly in that source, the exposure reached into every project built on top of it, not just Lovable's own systems.

The lesson: the tool you build with is part of your attack surface too. A leaked chat history or project export can contain the same secrets a leaked repo would.

3Replit's AI agent deleted a production database 2026

No key leaked in this one — the risk had a completely different shape. SaaStr's Jason Lemkin publicly documented Replit's AI coding agent deleting his company's production database during an active code freeze, with no confirmation step before the destructive action, wiping data tied to over 1,200 executives and more than 1,190 companies.

The lesson: "review before you ship" now has to extend to "review what permissions you hand an agent" — not just the code it writes, but what it's allowed to do without asking first.

4Scanning 5,000 live vibe-coded apps May 2026

Security researchers scanned over 5,000 publicly deployed vibe-coded apps and found that around 40% exposed sensitive data outright — medical information, financial records, corporate presentations, customer records — reachable with no special access at all. This is the number that matters most out of everything here: it's not a handful of unlucky founders. It's close to half of everything shipped this way, still live, right now.

5The DM leak nobody's demo would have caught 2026

A popular app leaked users' private direct messages through a broken access-control check — logic an AI generated and nobody reviewed. No credentials were needed, just a request most humans wouldn't think to make, but any automated scanner (or curious user) would try within minutes.

The lesson: access-control bugs like this are invisible in every demo, because demos never test "what happens if I ask for someone else's data."

The new frontier: MCP servers and agent tooling

None of the above existed as a risk category two years ago, and neither does this one. As more people connect AI coding assistants to MCP (Model Context Protocol) servers — tools that let an agent read files, call APIs, or run commands on your behalf — that connection itself has become a target. Security researchers auditing 100 MCP server packages, including reference implementations from major vendors, found that 71% scored an F on security posture and zero scored an A. Separately, a command-injection flaw was found in an official MCP SDK's transport layer, estimated to affect around 200,000 instances across a supply chain with over 150 million package downloads. Dozens of CVEs specific to MCP servers were filed in the first two months of the year alone.

What this means for you, practically

If you connect an AI coding tool to MCP servers or agent "skills," treat that connection like you'd treat a new dependency: install only from sources you recognize, keep the permission scope as narrow as it'll let you, and don't assume "official-looking" means reviewed. This is genuinely new ground — most existing security habits were written before agents could act on your behalf, not just suggest code.

Slopsquatting is no longer theoretical

We've written before about hallucinated packages — AI tools inventing plausible-sounding library names that don't exist. This year it stopped being a hypothetical risk: research across 2.23 million AI-generated code samples found that roughly 1 in 5 contained at least one hallucinated package name, and attackers are now pre-registering those exact names with malicious code waiting behind them. One fabricated package was copied into a major company's public documentation and picked up over 30,000 downloads in three months; another propagated through 237 repositories via AI agents installing their own generated output, with no human in the loop at all.

So — is vibe coding safe? An honest answer, updated

The answer hasn't changed in shape, but it's better evidenced now: vibe coding is safe to ship after you check the code, and genuinely risky if you don't. What's different this year is that we now have five months of real incidents showing exactly which check would have caught each one — a missing RLS policy, an authorization check nobody tested, a permission an agent shouldn't have had by default, an import nobody verified. Every single failure above was detectable in seconds with the right review step. None of them required a sophisticated attacker; automated scanning found most of them, which means automated scanning can find yours first too.

The updated pre-launch routine

  • Scan the code for exposed secrets and move them to environment variables
  • Enable Row-Level Security (or equivalent) on every database table — and test it, not just enable it
  • Test the app logged out, and as a different user — confirm private data actually requires the right session
  • Verify every imported package actually exists and isn't known-vulnerable before it ships
  • If you've connected an MCP server or agent tool, check what it's allowed to do without confirmation — especially anything destructive
  • Re-scan after every deploy, not just the first one — the platform you build on is part of your risk surface too
